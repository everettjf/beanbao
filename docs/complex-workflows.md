# Complex workflows: implementation plan

Updated November 2, 2026. This plan targets the on-device BeanBao Agent, App, sandboxed delivery browser, and RootHide Bridge on the connected iOS 26 phone. Research-to-PDF, email-draft generation, App Store listing handoff, and installed-bundle verification for a preinstalled app have been verified on the phone. Apple Mail composition awaits a configured account. The delivery browser has now completed visible Uber Eats search, merchant and item opening, required option selection, add-to-cart, cart opening, and read-only cart review. A separate checkout request stopped at Uber Eats sign-in. Checkout review and order placement remain unverified.

## Current boundary

The existing UI task path interprets a request as one canonical action. It can open four allowed apps, search Maps, or create a note. A separate research path now executes a bounded Palmino model/tool loop and persists its checkpoints. The Bridge still has no general app installation, file, purchase, or messaging route. Activity remains a bounded audit log; Sessions holds research, App Store, and delivery workflow progress, artifacts, and a read-only step history.

## Proposed execution model

Use a workflow coordinator in the mobile-owned Agent. The model may propose a typed plan and select the next available tool, while the coordinator owns execution, authorization, evidence, and persistence. Keep the SpringBoard Bridge limited to foreground observation and UI interaction. Put network research, artifact creation, and mail composition in dedicated Agent/App components instead of widening the Bridge into a general-purpose process runner.

### Reuse the copied Palmino runtime

The copied `PHKAgentRuntime` runs multi-step model/tool turns with call and time budgets, cancellation, conversation snapshots, and an execution checkpoint hook. `PHKToolRegistry` validates tool arguments against JSON schemas. BeanBao now supplies a Claude-backed `PHKModelClient`, typed research tools, and a private atomic `PHKExecutionCheckpointPersisting` journal. Tool receipts prevent duplicate local writes, and an uncertain write requires reconciliation. The policy still needs to expand one capability at a time for other workflow types.

The older `BeanBaoStepHarness` still uses `FixedStepModel` for bounded device actions. The new research route uses the actual Claude/Palmino tool loop. The service recognizes an explicit research/PDF request, creates a stable session ID, and the App exposes saved sessions, PDF preview, and optional Apple Mail compose. A model-classified natural App Store request can now enter the existing guarded lookup workflow while preserving the original request and task ID. Other compound requests still require purpose-built tools and routing; merely raising the 20-step limit would not make them reliable.

The workflow states are `planned -> running -> waiting_for_user -> running -> completed`, with `failed`, `cancelled`, and `needs_reconciliation` terminal or recovery states. Each step records a stable workflow ID, step ID, typed input, output reference, observed postcondition, attempt count, timestamp, and policy decision. Persist this record atomically in an app-private database. Do not store API keys, raw screenshots, or full page content in the default activity log. A separate, user-deletable session may retain the user's request, plan, source links, and resulting files for a configurable period.

Step execution has a bounded deadline and a postcondition check. Read-only steps may retry. Mutating steps get an idempotency key and must inspect the current state before retrying after a crash or disconnect. If the result is uncertain, stop in `needs_reconciliation`; do not click Pay, Install, or Send twice. Re-observe the screen before every UI action and after any app switch. A lock, SpringBoard restart, network interruption, or user takeover pauses the workflow and releases the wake lease. Resuming requires a fresh observation and revalidation of pending approvals.

The planner sees a capability manifest, not an unrestricted tap or shell tool. The first manifest should include:

| Capability | Execution path | Completion evidence |
| --- | --- | --- |
| `web.search`, `web.fetch` | Claude web search/fetch where supported, or a configured HTTPS search provider | Source URL, title, retrieval time, citation mapping |
| `report.compose` | Structured report sections with claims linked to sources | Schema and citation validation |
| `pdf.render`, `pdf.preview` | UIKit PDF renderer and PDFKit in BeanBao App | File exists, readable pages, visible preview |
| `mail.prepare` | Mail compose UI with recipient, subject, body, PDF attachment | Compose view and exact attachment/recipient shown |
| `app.lookup`, `app.open_store_page`, `app.verify_installed` | App Store product page and device inventory | Exact developer, app ID, and installed bundle verified |
| `delivery.search`, `delivery.configure`, `delivery.review_cart` | Per-app or per-site adapter built on restricted UI actions | Merchant, items, options, address, fees, and final total observed |

Tool inputs and outputs must be schema-validated. Web pages, search results, product descriptions, restaurant listings, and emails are untrusted data; text in them cannot add tools, grant permissions, or change the destination. The coordinator checks app identity, domains, addresses, recipients, amounts, and transition evidence independently of model output. Model-generated summaries are not proof of completion.

## Workflow-specific scope

### Research, PDF, and email

This is the first end-to-end target. Search current sources, fetch and deduplicate them, preserve source URLs and dates, draft a report with cited claims, render a multi-page PDF on the phone, and let the user inspect it. Prepare an email with the requested recipient and PDF attached. Apple MessageUI presents a Mail composer for the user to edit and send; its completion callback reports queueing in Mail, not delivery to the recipient. If Mail is not configured, leave the PDF available for export and mark the email step waiting for setup. An optional configured mail-provider API can be added later, with a separate explicit send approval and delivery status semantics.

Acceptance: a text request such as “Research on-device speech recognition on iOS, create a PDF with sources, and prepare an email to a specified address” creates one visible session. The PDF opens on the phone, has readable text and working citations, and matches the attachment in the compose screen. Canceling the composer does not mark the workflow sent. A network failure resumes from saved sources without restarting the whole workflow.

### App acquisition

Resolve the exact App Store app using its name, developer, and product ID; show the candidate before handoff. The native StoreKit product view displays the listing. Installing may require the user's App Store, Face ID, or password interaction. After the user finishes, query the installed bundle and verify that it is the selected app. Treat a paid app, subscription, sign-in, or unavailable regional listing as a user decision. Do not infer installation from the StoreKit view closing. Direct arbitrary IPA installation is a separate feature with different provenance and device risk; it is outside this workflow.

Acceptance: BeanBao identifies an exact free app, opens its official listing, waits without duplicating an install action, and reports success only after bundle verification. It reports a declined or unavailable install accurately.

### Food delivery

Start with one selected delivery app or mobile site. Implement its search, item/options, cart, and checkout review as a versioned adapter with screen checks; there is no universal reliable cross-app checkout path. At the review checkpoint show merchant, each item and option, delivery address, tax, fees, tip, total, and estimated arrival if available. Require an explicit, fresh approval tied to that exact snapshot before any order placement. If any amount, address, item, or merchant changes, invalidate approval. If confirmation is ambiguous, stop and ask the user to inspect order history; never repeat the final action automatically.

Acceptance: a scripted request reaches a correct cart and review screen without placing an order. A changed price or address blocks the approval. Only a later separately accepted live test may exercise final placement.

## Delivery sequence

As of November 2, source implementation and offline verification cover the workflow core, research-to-PDF path, email draft, App Store candidate selection and StoreKit handoff, and Sessions list/select/resume/delete controls. Tests use scripted Claude replies and web-search/App Store responses to verify citation rejection, PDF readability, checkpoint recovery, duplicate prevention, Mail result state, exact App Store candidate identity, and the rule that closing a listing cannot prove installation. Live Claude research produced a readable, linked PDF on the phone; a second live run produced a PDF and mail draft. Live App Store lookup opened the matching StoreKit listing and correctly stayed pending when closed. A separate Apple Mail lookup completed only after exact installed-bundle verification for the preinstalled app. On Pages, the official StoreKit **Get** action stopped at Apple ID sign-in; cancelling left the workflow pending and the bundle absent. The phone lacks an Apple Mail account, so composer and attachment acceptance remain open. A persistent delivery review gate has tests for changed merchant, item total, extra fee or discount, address, screen, approval expiry, and uncertain outcome after restart. The first Uber Eats adapter has now built and reviewed one disposable cart on the phone, and a later checkout request stopped at sign-in without reading credential fields. Installed-bundle confirmation after a fresh App Store install, Mail composer callbacks, and delivery checkout totals remain unverified.

Uber Eats is the provisional first delivery target. A prior browser trial using the public San Jose City Hall address reached item configuration and a disposable cart, while `Go to checkout` redirected to Uber account login. This does not establish a real delivery address, checkout charges, or a payable total. The versioned adapter rejects lookalike domains, login pages, and incomplete checkout observations. Its checkout review and approval tests use synthetic fixtures because the live checkout is behind sign-in. No order placement has been tested or authorized.

BeanBao App has a persistent WebKit browser and bounded, memory-only page snapshots. It refuses to read sign-in pages or pages with credential fields. The **Check** control classifies a fresh page through the on-device Agent without saving its text. The Palmino `delivery_choose` tool proposes one page-bound action. Before acting, the Agent validates a second observation and durably claims one attempt; after acting it requires an expected changed page. Uncertain actions cannot replay automatically. The private session journal contains proposals, page fingerprints, and transition receipts, not website text. Offline tests cover changed pages, duplicate prevention, constrained JavaScript actions, and an exact checkout review gate.

Agent 0.3.89 also limits option selection, cart mutation, and checkout navigation to actions authorized by the stored user request. The limit is applied to a new model proposal, a cached proposal, and the start of a browser action. If the request is ambiguous, these steps are rejected; the model still chooses the visible page action within that boundary.

The connected iPhone loaded Uber Eats after setting the public San Jose City Hall address. The sandboxed browser visibly completed feed → search suggestions → search → Phin & Bowl → Chicken Pho. A review-only run selected Rice Noodle and verified the required radio without adding an item. The first cart trial crossed a development Agent restart; it selected Rice Noodle, added one item, opened View order, and completed read-only review in two task records. Delivery Browser 0.1.14 then passed an uninterrupted text task from an empty cart through search, merchant and item opening, required option selection, exactly one add-to-cart, cart opening, and read-only review. After Agent 0.3.84 added a terminal check against the merchant, item, and option targets already executed in that workflow, a second uninterrupted full run passed. Its single journal completed with one `add_to_cart` transition, one `open_cart` transition, one `delivery_review_cart` receipt, and no checkout action. The visible cart contained one Chicken Pho, Noodle choice: Rice Noodle, and a $27.99 subtotal. No checkout or order action occurred.

The November 2 device investigation isolated the rendering failure to the App's `com.apple.private.security.no-sandbox` entitlement. With that entitlement present, the page DOM and accessibility tree populated, but the system screenshot showed a white viewport. Removing only `platform-application`, changing the initial WebKit frame, and forcing page repaint did not restore pixels. Removing `no-sandbox` made the Uber Eats page render and accept taps. A sandboxed App could then no longer connect to the Agent's Unix socket or use the existing shared model, hotkey, and PDF paths; a file-path exception entitlement did not restore the socket. These diagnostic packages were replaced by a separate sandboxed browser. No order was placed.

The separate sandboxed delivery-browser component keeps WebKit out of the privileged App while the existing App and Agent retain voice, session, PDF, and model paths. The App requests a fresh in-memory pairing token and opens the browser; the browser uses a restricted loopback channel for delivery observation, planning, verification, result, status, and stop operations. The Agent's general Unix socket remains separate. Tokenless loopback requests were rejected on the phone. The browser stops when it backgrounds, navigates off allowed Uber Eats hosts, or reaches login. The Palmino planner proposes one action from a fresh page; the Agent validates the proposal and a second observation before the browser clicks a unique visible control. After a page transition, the Agent records the verified result. A pre-click refusal closes the pending step without leaving the service blocked, while a possibly clicked action requires reconciliation. The live cart handoff tolerates changing merchant promotions by binding its plan to the exact store URL and option state, while the browser still checks one same-site cart link. Offline tests cover dynamic handoff text, changed store identity, duplicate prevention, selected options, constrained JavaScript actions, and the checkout review gate. Checkout totals must come from a fresh page observation; named signed adjustments are required when charges or promotions differ from standard fee fields. An unobserved or inconsistent total fails validation. Final order placement remains unavailable pending a separate approval and reconciliation gate.

1. **Workflow core:** typed plan schema, capability registry, persistent checkpoints, session and step status in App, stop/resume, deadlines, and a fake-tool integration test for interruption and duplicate prevention. Keep the existing single-task path unchanged while this is developed.
2. **Research to PDF:** source-aware web search/fetch, citation checks, structured report, on-device PDF rendering and preview. Test with a fixed research topic and inspect the generated PDF.
3. **Email draft:** recipient validation, attachment verification, native compose screen, cancel/send/queue state handling. Use a test mailbox for a separately approved send test; never use a real recipient from a research prompt without review.
4. **App Store handoff:** exact product resolution, listing display, installed-bundle verification, and clear pending states.
5. **Delivery adapter:** one named service, cart construction, exact total review, approval gate, and order-history reconciliation. Expand to other services only after each adapter is verified.

For the first release, the phone remains sufficient to execute a workflow once it has network access and an API key. A Mac is only a build and debugging tool. The model provides planning and interpretation; device-side code owns permissions and tool execution.

## External API evidence

- [Claude web search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool) can return current results with citations; capability and account availability must be checked at runtime.
- [Core Graphics PDF contexts](https://developer.apple.com/documentation/coregraphics/cgcontext) and [Core Text frames](https://developer.apple.com/documentation/coretext/ctframegetvisiblestringrange) render and paginate the on-device PDF. Quick Look previews it in the app.
- [MFMailComposeViewController](https://developer.apple.com/documentation/messageui/mfmailcomposeviewcontroller) supports a prepared message and attachment for user review, and does not guarantee delivery.
- [SKStoreProductViewController](https://developer.apple.com/documentation/storekit/skstoreproductviewcontroller) displays an App Store product page. This supports an installation handoff, not a promise of silent installation.
